# Instrument access

Use APIs only for the Joulescope JS110 and Saleae Logic Pro 8. The user requested this on October 16, 2026. Do not use computer-use tools, screenshots, mouse clicks, or keyboard automation to operate these instruments unless the user changes this preference.

- Saleae: use `saleae.automation` through the existing Logic 2 server on localhost port 10430. Logic 2 remains the instrument backend; API-only does not mean the application can be closed. Reuse the running instance and save captures and exports programmatically.
- Joulescope: use `pyjoulescope_driver` directly. Only one client should own the device. If the GUI owns it, use a documented release mechanism if available, or request the minimum manual release; do not silently revert to computer use or force-terminate an application with unsaved data.
- Preserve instrument settings and target power during ownership changes. The existing JS110 helper opens in `restore` mode and preserves its starting current range. A successful API command is not proof of physical power restoration: verify the measured rails.
- Multiple chats share this physical bench and workspace. Check existing helper/capture ownership before changing power, firmware, or instrument state. Do not stop another chat's session merely because work in the current chat is read-only. Resolve competing hardware activity with the user before taking control.
- Hardware update, October 18: the user reports **D2 and R23 removed**. Other assembly rework is not yet reported. Historical D2 target-to-ST-LINK supply statements no longer describe the current board; signal/sense paths still remain. Keep CN10 independently powered for development. CN8-only operation with CN10 unplugged is an unqualified functional-test configuration: FT pin voltage tolerance does not establish powered-off leakage or transition behavior, and a near-zero debugger rail alone does not prove zero interface current. Verify actual interface loading/supplies/reset/capture before assuming prior power measurements still apply. See the [updated audit](docs/power/nucleo-debug-isolation.md#d2-and-r23-removed-cn8-only-functional-operation--october-18).
- Hardware clarification, October 19: the user confirms the GPIO banks are **still at 3.3 V** and will use the existing seven-pin SD breakout **without socket rework**, prioritizing one-bit throughput. The [current plan](docs/prototype/sd-breakout-benchmark.md) is **native one-bit SDMMC2**: SCK/CLK→CN3.3/PC2, DI/CMD→CN3.25/PC3, DO/DAT0→CN3.13/PC4 (AF11); CS/unused DAT3→CN3.21/PE4 as input/pull-up, VCC→CN5.4/3V3, GND→CN3.19, CD unconnected. No CN3.15/17 or hidden socket wires. Retain SB23 and VDDIO5 at 3.3 V. This supersedes the earlier four-bit and Arduino SPI5 experiments; do not negotiate four-bit or UHS 1.8 V mode. The carrier's absent unused-DAT1/2 bias network remains a bench qualification limitation, not a reason to assume physical rework was done. The user subsequently reports SD pins attached, ST-LINK USB connected and target power through JS110. Exact source routing, rails and SD operation are not yet measured; no SD firmware has been installed. Keep the existing NAND choice pending comparison.
- Recovery wiring update, October 19: the user reports the JS110 OUT0 recovery wire no longer reaches and requests an **ST-LINK-controlled** replacement. Do not assume PE1 recovery is externally selectable in this setup. The existing VCP TX path goes through R24 (33 ohms) to **PE6 / USART2_RX**, also accessible at CN15.2 through SB34. A boot-prefix detector on PE6 is proposed, not implemented or qualified; current v44 still checks PE1. ST-LINK-V3EC has no documented spare host-controlled GPIO here; RTS/DTR are not a supported substitute, and continuous UART BREAK support has not been established. See [the proposal and validation limits](firmware/capture-timing/recovery_gpio/README.md#october-19-proposed-st-link-vcp-recovery). Recheck ownership, power/probes and an effective recovery path before risky firmware experiments.

- Avoid manual recovery blockers. After a finished ST-LINK client reports `DEV_USB_COMM_ERR`, use the guarded `firmware/boot-timing/stlink_recover.py --execute` helper once and verify a bounded HOTPLUG AP1 read before asking for a cable reconnect. This recovered the observed October 17 failure. It only clears this debugger's WinUSB pipes; it does not guarantee recovery from every hang. Do not reset the shared USB hub. See `firmware/boot-timing/stlink-recovery.md` for identity/ownership guards and the historical D2 supply path (D2 was subsequently removed on October 18).
- Do not repeat the standard Nucleo external loader's full initialization in the normal-boot diagnostic state: it stalled and left the debugger transport unresponsive. Prefer individually verified, bounded RAM operations that preserve the working ROM clocks, security and XSPI routing; read and compare data before enabling any flash write.
- Do not read CSI registers while RCC holds CSI in reset or its required clocks are disabled. The v30b diagnostic stalled at that access; v30d and later snapshots first check RCC and mark skipped reads explicitly. The documented v30 recovery used a measured debugger reset pulse to reach an exact, verified prefix failure before receiver/DMA or NOR-transfer startup. That is a separate recovery case, not permission to bypass the completed-capture or failed-PHY maintenance guards. See the [v30d recovery evidence](firmware/capture-timing/evidence/2026-10-17-v30d-phy-sequence/README.md#recovery-evidence).
- Preserve the hardware-qualified [PE1/CN15.24 recovery guard](firmware/capture-timing/recovery_gpio/README.md) in every new experimental image. The original v34c prefix passed normal capture, externally selected early recovery, and actual NOR erase/program/readback from that recovery state on October 17. The user's diode connects PE1 anode to OUT0 cathode: shared GPIO supply 3300 mV, OUT0 HIGH for normal boot and LOW for recovery. Supply-off with retained OUT0 low did not release PE1; do not treat that as floating. The helper restores its starting settings, so explicitly verify the final normal-selection state. Keep the working BOOT jumper position unchanged. Both branches worked in the October 17 setup; the changed October 18 physical recovery path needs renewed verification. Historical baseline images lack this guard; the generic builders do not enforce it yet, so verify the exact guarded prefix and metadata before programming a new experiment.
- Early recovery precedes expanded SRAM setup. Use `recovery_gpio/check_park.py` to check exact live code/status/park, CPU context, disabled caches and idle XSPI before the frozen low-SRAM NOR helper. Do not use the normal high-SRAM maintenance helper there. v34b selected recovery correctly but retained the ROM I-cache and failed the maintenance gate; v34c disables/invalidates it only on the recovery branch. CubeProgrammer can resume execution on disconnect: combine halt and a halt-dependent operation in one CLI connection, and never infer a persistent halt from an earlier call. The verified branch-to-self park remains safe if resumed.
- Normal-boot maintenance now works through explicit HOTPLUG `ap=1` with the awake revision-2 marker image. Use the reviewed `firmware/boot-timing/nor_bench.py` and its documented fixed RAM helper for these first-64-KiB experiments. It verifies current/desired contents before erase and full readback afterward. Never halt, reset or remove power from a possibly active NOR operation. Keep helper instructions byte-identical between executions with I-cache enabled, or start from a fresh cold boot. Prefer leaving a verified image with post-marker debug access so subsequent work does not require manual BOOT1 changes; retain the original exact backup.
