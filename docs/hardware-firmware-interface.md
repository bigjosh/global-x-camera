## Current behavior and firmware contract

**D-37 implementation boundary:** use C and STM32CubeN6/HAL as the initial bring-up base. Keep camera, storage, power/control and USB hardware access behind simple replaceable interfaces so timing/energy-critical paths can move to LL/direct-register code or streamlined bare-metal startup/runtime without changing the accepted behavior. HAL use and RTOS use are separate choices: bare-metal firmware can use HAL, and this decision does not select an RTOS or USB middleware. ST documents HAL/LL and optional middleware separately in [STM32CubeN6](https://github.com/STMicroelectronics/STM32CubeN6); its [driver component](https://github.com/STMicroelectronics/stm32n6xx-hal-driver) supports selecting needed functions.

Measure shutter-button press from fully powered off to the saved exposure's start, later readout/save/shutdown intervals, and energy per complete capture under equivalent exposure/configuration and verification settings. Use those results to prioritize startup, driver or runtime changes; no savings follow merely from the label “bare metal.” Retain required hardware delays, integrity/commit checks, fault behavior and shutdown sequencing. D-40 selects 16-bit grayscale PNG export. Hardware integration, measured compliance, encoder integration and exact runtime/USB choices remain open.

**Retention, approved October 14:** successfully committed photos and the metadata needed to recover them must survive **ten years at room temperature (approximately 25°C reference), fully unpowered, with no refresh needed**. No periodic wake, battery/RTC supply, USB connection or maintenance write may be required for photo retention. Implement the selected device's ECC and qualify both data and metadata through **1,000 complete fill/download/explicit-erase cycles**, approved October 14; the minimum 200-photo capacity implies 200,000 photo saves. Account for actual block and metadata wear. The accepted policy uses host-requested full-image RAM reads and predictive-error slot retirement without relocation or refresh; exact-part thresholds and retention limits remain to qualify. See [retention review](decisions/storage-retention-review.md) and [spec.md §6.7](../spec.md#67-photo-retention--approved-october-14-2026).

**Capture and capacity:** STM32N6 remains active; Himax is abandoned. The prototype uses CAM-6G3-073CLR / VD56G3 with 73° diagonal field of view and uncompressed packed RAW10 at full native resolution. Retain at least 200 photos between downloads. Each packed image payload is 1,916,420 bytes before metadata; actual capacity, NAND part/interface, allocation and reserve policy remain to be qualified. The former 644 × 604 VD55G0 image describes the recovered circuit only.

**D-44/D-45 — cold-start constraints, approved October 15:** use only the newest image-sensor revision, confirmed during factory commissioning. Optimize the bootstrap loader for minimum practical size and startup time, and optimize the size, placement and loading order of additional code. Start sensor initialization before loading code needed only later, such as NAND payload programming. Overlap later loading with sensor hardware waits where safe; do not require the full application to load before sensor initialization begins. Exact memory layout and staging remain implementation work, and the 50 ms target still needs measurement.

Factory commissioning must read and record actual sensor identity/revision and compare it with the expected newest revision for the production build; older or mismatched sensors do not pass commissioning. The inspected driver currently identifies cut 3 (`0x31` upper revision byte) as fast boot. This evidence is not a permanent definition of “newest”: update the expected identity and supported startup path when silicon changes, and verify that the qualified path still fits the timing requirement. No new runtime LED code or cold-start revision scan is prescribed by this commissioning decision.

The early boot stage must retain HOLD takeover, required rail/clock setup, sensor initialization and dependencies needed to meet exposure timing. Establish trustworthy storage availability before exposure under the existing full-storage policy; a small metadata/read path may therefore be needed early even when NAND payload-programming code loads later. CSI/DMA/buffer setup must be ready when the sensor produces data. Later loads must not block critical sensor transactions or overwrite executing code, active DMA buffers or required interrupt state. The loader strategy, code placement and use of hardware waits are to be measured and implemented; no specific overlay, DMA loader, FSBL byte limit or memory map is frozen.

**Timing and input:** with USB disconnected, a shutter press starts the main supply; it must last until early firmware establishes GPIO HOLD. From fully powered off, **start of exposure must occur within ≤50 ms of the shutter-button press**. Qualify this deterministic design budget; no runtime timing-error code is selected. Exposure duration, frame readout, save and shutdown are measured separately afterward. Ignore additional presses during capture/save, finish the current operation unless a fault requires abort, and queue no exposure. A new capture requires an actual power cycle of the main capture electronics after shutdown and a fresh press after ready; a busy press held through completion must not become a deferred shot.

**D-36 — prototype exposure time:** use a potentiometer connected to an MCU ADC input. Sample it before acquiring the image, map the reading to exposure time and apply that setting before the saved exposure begins. D-50 (October 24) supersedes D-38 with a second slider for manual 1×–8× analog gain, keeping digital gain at 1×. D-39 retains exponential exposure from the fastest supported setting to 1 s. Sample and latch both controls before applying sensor parameters for the first exposure; D-51 selects the ADC arrangement below while gain-control firmware remains to implement. See the [gain decision](prototype/NOTES.md#2026-10-24--give-the-gain-slider-the-full-analog-range-while-retaining-unity-digital-gain). D-51 selects 10 kΩ linear sliders: exposure on conditioned Arduino A0/CN4.1, gain on A1/CN4.2, bottoms at ground and high ends on one switched 3.3 V GPIO. Keep companion PF5/PC10 high impedance/no pulls. After the analog supply is ready, enable the pots, allow settling while independent initialization runs, sample and latch both, drive the pot supply LOW, then apply the sensor settings. Calibrate endpoints and test variation between the separate GPIO-supply and ADC-reference rails. The exact shared GPIO, part, filtering, invalid-input handling and measured ADC/sensor timing remain to qualify. See [D-51 control-interface decision](prototype/NOTES.md#2026-10-24--use-conditioned-arduino-analog-inputs-and-switch-both-control-pots-together). Include input/reference startup, settling, sampling and sensor setting application in the existing ≤50 ms exposure-start budget. The control circuit must meet the existing main-path OFF-current requirement; no permanently battery-powered divider is selected. Record the exposure/configuration actually used in the existing single photo object. A0/CN4.1 reaches PA8/ADC12_INP5 and A1/CN4.2 reaches PA9/ADC12_INP10 through the board conditioning; do not apply header-level 3.3 V directly to those raw ADC pins. Exact shared supply GPIO remains to assign; the historical pin table below does not define these new controls.

An initial firmware mapping candidate for normalized knob position `x` from 0 to 1 is `t(x) = t_min * (1 s / t_min)^x`. This gives equal exposure ratios for equal knob movements and smaller absolute time changes at the fast end. Clamp/quantize to supported sensor timings and record the actual applied exposure. The user selected the exponential behavior and endpoints, not a frozen formula, numeric minimum or physical logarithmic potentiometer. Verify that the selected clock/mode and frame-length settings permit one-second integration. The ≤50 ms deadline concerns exposure start; the exposure itself may last one second. D-50 selects manual analog gain from 1× to 8×, quantized to the 29 supported codes; digital gain remains 1×. Latch both settings for the photograph; no automatic gain/exposure loop is selected.

**D-43 — USB detail review deferred, October 15:** defer PNG/PTP implementation details until firmware bring-up. Keep the selected PNG/PTP behavior and early bring-up checks for host interoperability, current-read warning/filename timing, compressed object size and RAM use. This postpones implementation choices, not those requirements. The next review is the ≤50 ms cold-power-to-exposure-start target; physical prototype modifications remain paused until the board is in hand.

**D-40 — USB export, approved October 15:** generate 16-bit grayscale PNG with lossless compression while USB-powered. Preserve all ten sensor bits; NAND retains the single uncompressed packed-RAW10 photo object. For each host image-data request, read NAND freshly into RAM, check it, then encode that result with the accepted metadata/recovery warnings. Exact reversible sample mapping, encoder/workspace, PTP length handling and host interoperability remain implementation work.

**D-48 — current Nucleo phase indication, approved October 18:** use active-low LD5/PG10 red from the earliest custom-boot code until first exposure, LD7/PG8 blue from the first sensor STROBE rising edge until the first complete frame is in RAM, and LD6/PG0 green only during actual future NAND writing. All three are off at sleep/shutdown. The ROM phase precedes firmware control; sensor START and receiver arming are not exposure-start markers. The RAM-only capture build must never show green or claim a save. This supersedes D-41's flashing yellow and 250 ms green sequence for this prototype, while retaining product fault blink counts and storage-full behavior. Keep indication nonblocking, and qualify latency, optical contamination and energy on the exact image.

**Current implementation boundary, October 18:** v44 is programmed with full 64 KiB readback verified, and the user reports the LEDs working. Its all-off shallow WFI completion path intends to retain RAM/debug; actual sleep, debug retention, full-frame capture and PE1 recovery still need instrumented checks. Minimum-power shutdown, Standby/HOLD release and regulator turn-off remain unimplemented. Bench work is stopped while the user continues board modifications; recheck supply, probes and recovery wiring before tests. V41 remains the last instrument-qualified image; see the [checkpoint](../firmware/capture-timing/README.md#october-18-checkpoint--v44-installed-leds-confirmed-by-user).

**Storage:** preserve existing committed photos and refuse new captures when no usable slot remains; show seven red flashes for full and enter shutdown (D-42), without taking a new photo or showing green success. Capacity exhaustion alone does not retire slots or authorize erasure. Full payload readback plus checksum comparison is configurable and enabled by default during bring-up/initial testing; it may be disabled later. In either mode, generate integrity metadata/checksums, wait for program completion, check status/failures, perform required ECC/bad-block/recovery handling, and read back and verify the final durable commit record before successful-save shutdown. ECC status does not verify an unread payload. The criterion for later disabling full readback remains unsettled; firmware and the final storage format remain unimplemented.

**Power and shutdown:** four series CR2032 cells through LTC3621 are selected. The room-temperature 100 nA OFF target applies to the complete main path, including regulator and external pack-connected leakage; retained RTC cell-tap backup is additional and must be measured/budgeted separately. After safe save, prepare peripherals and shutdown configuration, then enter genuine N6 Standby while an ordinary HOLD GPIO remains driven until entry. Standby makes that GPIO high impedance; Stop retains its configuration. Retain external pulldowns, select a pin outside the documented exceptions and prevent held-button wake retriggering. In the existing divider/HOLD concept, a held button keeps the buck enabled until release. External PWR_ON/AUX sequencing and any optional RUN-to-ground shutdown delay remain unimplemented: AUX must discharge below 0.6 V before main supplies leave their valid range. See [power.md §6](../power.md#6-camera-integration-requirements).

**Shutdown definition and F-01, approved October 13:** shutdown is the lowest attainable power state, with an actual power cycle of the main capture electronics required before another image; RTC backup may remain powered. A held button waits for release to permit main power-off, with no automatic wake/retake. At any phase of a cycle, including post-save shutdown, detected low battery requires **one red LED flash**, then abort to shutdown. This abnormal abort must not wait for successful image commit. Preserve existing committed photos, including the current image if already valid and durably committed; never report an incomplete or unverified image as saved. Interrupted writes follow the accepted USED/DONE policy; physical encoding, conservative recovery and device qualification remain open. Indication and controlled shutdown require enough remaining power, not a guarantee after rail collapse. Battery sensing, thresholds and warning/hold-up energy remain to be implemented and qualified. The recovered [BOM](../bom.txt) has green/yellow-green **LED1, ROHM SML-P11MTT86R**; a red-capable indication must be selected and qualified, with no CAD/BOM change made here.

**F-02 abrupt power loss, approved October 13:** the current uncommitted image may be incomplete, but preserve previously saved photos and an already validly committed current image. **Keep any bytes written to NAND.** Mark blocks **USED at save start** and **DONE at successful completion**; USED without DONE identifies possibly corrupt/incomplete data. On restart recover valid, complete, durably committed photos, without silently erasing/discarding incomplete raw bytes or automatically taking a replacement exposure. Excluding incomplete data from successful-photo recovery does not permit physical deletion. Marker layout/encoding, NAND geometry, reclamation and recovery remain unimplemented; qualify torn markers, programming limits, shared-block effects and preservation of older photos. USED/DONE does not replace mandatory status/integrity checks or final commit-record readback verification. No hardware guarantee, final-write opportunity or LED indication after abrupt collapse is assumed. See [spec.md §6.5](../spec.md#65-f-02-abrupt-power-loss--approved-october-13-2026).

**Failure map, approved October 13:** low battery at any phase = **1 red flash**; camera initialization = **2**; frame capture = **3**; storage unresponsive = **4**; new-photo write, enabled-readback or commit failure = **5**; damaged allocation metadata/index = **6**. These faults enter the defined shutdown state after indication where power permits, require a main-capture power cycle before another image, and do not trigger an automatic retake. D-48 selects phase indication for the current Nucleo prototype; it does not change these product fault counts. Red flash duration/spacing and fault implementation remain open. No automatic retry is selected. If time or orientation is unavailable/invalid, record an explicit **BAD sentinel**, still save the image, and omit that unavailable EXIF field when presenting the photo over USB. Report existing-photo read failures to the host during USB reads; report explicit-erase failures/interruptions through USB. Reading a photo does not authorize erase. Boot failure/firmware hang has no selected recovery requirement; this does not assert technical impossibility. See [spec.md §6.6](../spec.md#66-remaining-failure-responses--approved-october-13-2026).

**USB, updated October 14:** use a **USB-powered PTP camera interface with explicit per-photo deletion**, replacing drive/filesystem emulation. The shutter remains inactive. Serve committed photo objects and handle explicit host delete requests; durably record logical deletion before acknowledging success, then reclaim NAND space safely. Connecting USB or downloading alone never deletes photos. D-40 selects 16-bit grayscale PNG; encoder integration, object handles, error mapping and safe reclamation remain implementation work; see [accepted USB interface](decisions/usb-photo-access-review.md). Insertion/removal during operation is allowed without an assumed seamless power guarantee. USB detection, source isolation and keeping the battery converter disabled remain hardware integration work, including the Nucleo test arrangement.

**Read integrity, approved October 14 and refined:** each USB host image-data request freshly reads the whole original NAND image into RAM, checks ECC/CRC-32C, then exports that snapshot with current-read filename/EXIF warnings. A later request rereads NAND and may differ. No background payload scans, relocation or refresh. Predictive media errors permanently retire the whole slot from future image writes while preserving current read access; only explicit host deletion removes the photo. Safe metadata reads/writes and capture-time verification remain separate. RAM sizing, predictive thresholds and same-request PTP filename behavior need qualification; see [read policy](decisions/ecc-read-error-review.md).

**Deferred directions:** VD5943/custom optics, spring-driven mechanical frame advance and FD-03 series-capacitor pulse start remain future work. FD-03 could permit shutdown despite a held button; it is not the optional RUN-to-ground delay and does not replace the current divider/HOLD baseline. No capacitor values or SPST-reset-bleed/SPDT arrangement are selected.

The recovered specification records a 40 MHz HSE, execution from internal SRAM after early boot loading, and primary/redundant FSBL locations of `0x00000` / `0x40000`. Reconcile these inherited implementation inputs with boot ROM behavior and the existing firmware; they are not independently validated boot settings.

The recovered VD55G0 camera connection uses one CSI-2 data lane plus differential clock, a 1.8 V configuration bus, an MCU-generated master clock and shutdown/analog-enable controls. Its historical sequence keeps shutdown asserted, establishes core and I/O rails, delays analog enable by approximately 1 ms, establishes MCLK and releases shutdown. Do not carry these values into VD56G3 unchanged: verify the selected module's supplies, connector, supported lane/mode, clocks, register sequence and exposure-start timing.

## Work sequence while firmware is integrated

1. Use the completed KiCad reconstruction and its evidence as the historical starting point. Apply the selected camera/power integration and confirmed electrical corrections, recording intentional connectivity changes separately.
2. Review the revised supplies/latch, default states, voltage domains, pin functions, boot wiring and footprints. Use the integration table to resolve interfaces that can change copper.
3. Establish placement groups, decoupling and power-loop placement, BGA escape feasibility, camera/USB routing corridors, and mechanical reserves using a conventional four-layer process as the working target.
4. Reconcile the firmware's existing pin/clock configuration, boot/startup sequence, sensor mode, and storage integrity design when those artifacts arrive. A concise pin map and startup timing outline are useful even before the complete firmware tree is integrated.
5. Freeze affected pin assignments and high-speed routing constraints after their checks; obtain actual fabricator stackup and manufacturing rules before final routing geometry and release verification.

Firmware integration runs alongside hardware work. It is required to validate the shared interface and end-to-end behavior; it does not block circuit corrections, footprint validation or placement planning. The 1.6 mm/four-layer PCB is provisional, and the ≤5 mm finished-product thickness is a design target that may be exceeded by the functional prototype.
