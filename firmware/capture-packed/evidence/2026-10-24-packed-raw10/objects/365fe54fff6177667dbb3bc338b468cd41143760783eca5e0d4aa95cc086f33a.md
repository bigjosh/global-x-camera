# Packed RAW10 register audit — 2026-10-24

Offline research only. No hardware operation was performed for this note. No
canonical firmware was changed. Root and folder searches found no NOTES.md.

## Conclusion and proposed experiment

The sensor already transmits RAW10 packed on CSI-2. The normal STM32 receive path
does two transformations: CSI LLP rearranges the MIPI five-byte groups into a
contiguous 10-bit bitstream, then DCMIPP Pipe0 expands each pixel into 16 bits.
Pipe0 PAD controls **alignment**, not whether expansion occurs.

The best candidate to bypass both transformations is:

1. Keep sensor FORMAT_CTRL `0x030A = 10` (RAW10 wire encoding).
2. Set sensor OIF_IMG_CTRL `0x030F = 0x30` (user-defined CSI data type).
3. Configure CSI VC0 as BPP8, so its LLP treats the incoming payload as bytes.
4. Filter Pipe0 on `DTIDA = 0x30`, with no crop, decimation, header insertion,
   byte swapping, or double-frame-buffer mode.
5. Capture to a 16-byte-aligned buffer and verify the payload length, complete
   frame, error history, post-buffer guard, deterministic test-pattern pixels,
   and a real visible image.

This is a **proposed experiment**, not a claim that this combination has worked.
UM2602 section 16.1 says active image and status data may use different data types
through OIF controls, and lists output format independently. Its register table
gives a writable six-bit image DT. It does not explicitly qualify arbitrary
user-DT + RAW10 operation; the exact combination needs the bench test.

Useful modes to distinguish the stages:

| Sensor depth | Sensor DT | CSI format | Expected interpretation / purpose |
|---|---|---|---|
| 10 | 0x2B | BPP10 | Existing proven padded16 reference |
| 10 | 0x2B | BPP8 | Negative/control test: likely still pads because Pipe0 sees RAW10 DT, but CSI ordering is now wrong for that unpacker |
| 10 | 0x30 | BPP8 | Candidate original MIPI RAW10 five-byte groups in RAM |
| 10 | 0x30 | BPP10 | Optional diagnostic: candidate contiguous 10-bit bitstream, with CSI reorder but no Pipe0 expansion |

The second row's expected behavior is an inference. The explicit hardware
register descriptions separate CSI format/reordering from DCMIPP's DT filtering,
but the documentation does not directly describe this deliberate mismatch.
Changing Pipe0 DTMODE to ALL does not provide a format override; it only changes
which packets are accepted. Pipe0 has no FDTF/FDTFEN override. Those fields and
HAL_DCMIPP_PIPE_CSI_ForceDataTypeFormat exist only for Pipe1/Pipe2.

## Exact sizes and byte layout

For current 1120 x 1364 capture:

- Pixels: 1,527,680.
- Existing padded16 RAM: 3,055,360 bytes.
- Packed10 RAM: **1,909,600 bytes**, a reduction of 1,145,760 bytes / 37.5%.
- Packed line: 1,400 bytes = 350 32-bit words. No end-of-line word padding is
  required at this width. This is not a claim of 16-byte row pitch: Pipe0 has no
  programmable pitch, and a 1,400-byte line is 8 modulo 16.
- Dump limit for exact packed payload: **477,400 words**. P0DCLMTR.LIMIT is in
  32-bit words; P0DCCNTR reports bytes. A first uncertain-format experiment can
  retain the existing safe padded16 allocation/guard rather than falsely assuming
  packed length before it has been observed.
- Whole SD sectors: 3,729 full 512-byte sectors plus 352 bytes; fixed sector
  storage requires 3,730 sectors / 1,909,760 bytes, with 160 bytes of tail padding.
- Every 64 lines is 89,600 bytes = 175 SD sectors exactly. Every 32 lines is
  44,800 bytes = 87.5 SD sectors. A 32 KiB write need not be line-aligned, provided
  the producer has demonstrably completed those bytes.

Original MIPI RAW10 group, four pixels per five consecutive bytes:

```
b0 = p0[9:2]; b1 = p1[9:2]; b2 = p2[9:2]; b3 = p3[9:2]
b4 = p0[1:0] | p1[1:0]<<2 | p2[1:0]<<4 | p3[1:0]<<6
```

If CSI remains BPP10, this is **not** the output byte ordering: CSI rearranges
into consecutive little-endian 10-bit samples as shown in RM0486 Figure 432.
Both 10-bit layouts are lossless but the raw-file metadata/decoder must identify
which one was actually observed.

## Relevant STM32 registers / HAL

- `HAL_DCMIPP_CSI_SetVCConfig(&hcam, VC0, DCMIPP_CSI_DT_BPP8)` writes
  `CSI->VC0CFGR1 = (2 << 8) | 1 = 0x201`: ALLDT=1, CDTFT=BPP8.
  This setting must be established before VC0 is running; changes while running
  are ignored (RM0486 40.9.3).
- Existing BPP10 equivalent is `0x301`.
- `HAL_DCMIPP_CSI_PIPE_SetConfig` with DTMODE_DTIDA and DataTypeIDA=0x30 uses
  Pipe0 DT filtering; it does not alter the received packet's format tag.
- `HAL_DCMIPP_PIPE_EnableLimitEvent(..., DCMIPP_PIPE0, byte_limit / 4)` sets
  the limit/interrupt. Limit overflow drops data until frame end, so a limit
  event is a failed capture, not usable completion.
- `P0PPCR.PAD` bit5: 0 right aligned / 1 left aligned for padded10/12/14.
- `P0PPCR.HEADEREN` bit6: must remain0 for a pure raw pixel payload.
- `P0PPCR.DBM` bit16 swaps frame base addresses at **frame starts**. It is not
  an intra-frame two-block ring buffer.
- RM0486 section39.7.9 / page1870 explicitly limits the intra-frame ping-pong
  feature using LMAWE/LMAWM to **pixel pipes only**. The writable P0PPCR reserves
  bits31:17, and the CMSIS header has no P0 LMAWE/LMAWM definitions. The read-only
  P0CPPCR table nevertheless describes such fields; do not treat this apparent
  documentation inconsistency as permission to write reserved P0PPCR bits.
  Packed Pipe0 can use a contiguous frame buffer with consumers reading completed
  prefixes, but a small wrapping ring is not documented for that pipe.
- `P0PPM0AR1` base address must be multiple16.
- `P0PPCR.LINEMULT` bits15:13 gives events after1,2,4,8,16,32,64,128lines;
  `HAL_DCMIPP_PIPE_EnableLineEvent(..., DCMIPP_MULTILINE_64_LINES)` uses6<<13.
  The final partial group also emits a line event at frame end.
- FRAME completion is explicitly defined at the pipe output after the last
  pixel was written on AXI (RM0486 39.4.7). LINE is described as completed
  line(s), but this audit did not locate an equally explicit AXI-completion
  statement for Pipe0 LINE. Section39.7.9 describes a safe consumer triggered
  after16lines are written, but that example explicitly concerns pixel pipes.
  The Pipe0 streaming implementation must qualify the boundary before an SD
  DMA consumer reads freshly produced bytes.
- P0DCCNTR is copied to a readable shadow at frame end. Do not assume it is a
  live monotonically increasing producer-position register.
- P0STM0AR reports the last frame base, not a live DMA write pointer.

## Deterministic verification

Pipe1/Pipe2 reduce the high-dynamic data to8bits/component, so they cannot
provide an exact same-frame 10-bit reference alongside Pipe0. Even two full
packed+padded buffers would need4,964,960bytes before code/stack, beyond current
4MiB contiguous frame SRAM budget. Use independently repeated sensor digital
patterns and download the captures between tests.

ST's bundled `vd6g.c` and ST's Linux `vd56g3.c` agree on:

- PATGEN_CTRL0x0400: horizontal grayscale0x0101, vertical0x0111,
  diagonal0x0121, pseudorandom0x0131.
- Disable Duster with0x0318=0.
- Set DARKCAL_CTRL0x0340=2 (disable dark averaging), matching both drivers'
  test-pattern setup.
- Prefer diagonal plus horizontal/vertical ramps over a constant image to check
  byte order, row boundaries and all four low-bit phases. Prove full10-bit
  variation exists in the actual reference; an8-bit ramp would not validate
  lowbits. A pattern repeat should be byte/pixel-identical before it becomes a
  reference. PN28 repeat/seed behavior is not established here.

Documentation discrepancy: UM2602 Rev8 sections14.4 and status mirror table give
the above pattern encodings; its dynamic-register table on page61 instead lists
0x20/0x21/0x22 for grayscale types. The actual shipped Cube and official Linux
drivers both use0x10/0x11/0x12. Qualify this choice on hardware and record the
readback and resulting image rather than assuming either table proves it.

## Offline experiment source review

Reviewed `experiment/build.py`, `experiment/experiment.c`, `experiment/protocol.py`,
and generated `native10-diagonal-v3` receiver/sensor source after the builder's
readback update. No blocker was found in the native/passthrough register choices
or count arithmetic. This review does not qualify hardware behavior.

- The sensor is reset, booted to SW_STANDBY, given FORMAT_CTRL10 and the selected
  DT, then test-pattern controls are written before START.
- The pattern setup disables Duster and sets DarkCal2 before PATGEN0x0121; no
  subsequent sensor initialization overwrites those registers.
- Native expected output is3,055,360bytes; opaque expected output is1,909,600.
  Both builds now reserve the full existing padded16 allocation and set the
  DMA limit at that safe allocation boundary. The expected-payload guard and a
  separate allocation-end guard are checked. This allows diagnosis of a failed
  opaque interpretation without a DMA overwrite beyond the reserved frame.
- Sensor FORMAT_CTRL, DT, PATGEN, Duster and DarkCal are read back after capture.
  The proof contains PATGEN; extended RAW10 diagnostics retain all three pattern
  control values. Hardware output still must prove low-two-bit correctness.
- Existing first-frame capture checks, error history, receiver stop, idle checks
  and sensor STOP remain. SD/NOR SAVE handoff is removed from the RAM experiment.
- P0FSCR in the proof is the snapshot taken before stopping the pipe; PIPEN may
  still be set in that snapshot. The live post-stop PIPEN is separately checked
  by `raw_experiment_complete`, so a host check must not reinterpret the earlier
  snapshot as a final idle-register sample.
