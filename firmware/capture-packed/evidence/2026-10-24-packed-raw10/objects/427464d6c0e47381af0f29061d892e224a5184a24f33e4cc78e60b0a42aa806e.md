# Packed RAW10 capture to SD: offline pipeline audit

This is an offline audit, not a hardware qualification. No instruments, target
memory, firmware, card data, or power state were accessed or changed by this audit.
The independent packed-RAW capture experiment must establish whether the exact
CSI/DCMIPP byte interpretation preserves sensor samples without CPU repacking.

## Quantitative consequences

For the current 1120 x 1364 image, true packed RAW10 is 1,909,600 bytes, compared
with the current 3,055,360-byte padded-16 capture. The saving is 1,145,760 bytes,
or 37.5% of frame RAM. A row is 1,400 bytes if no inter-row padding/header exists.
The payload is 3,729 complete 512-byte sectors plus 352 bytes: a raw block stream
therefore uses 3,730 sectors with 160 final padding bytes. Record true length,
dimensions, packing order, exposure and other metadata separately or in a fixed
header. A 512-byte header keeps the image payload sector-aligned; it is a format
proposal, not a settled choice or qualification.

The v66c source-ordered external trace observes 21.861 ms from STROBE IRQ to
complete-frame IRQ. This includes exposure/interrupt effects, so using all of it
as transfer time is generous to the proposed streaming pipeline. The resulting
average packed production rate is at least about 87.35 MB/s over that envelope.
Actual instantaneous MIPI/AXI bursts can be faster.

The measured current one-bit SD driver throughput is 2,649,960 bytes/s. At that
rate the packed payload needs 720.615 ms, excluding initialization, filesystem
setup, final close/sync, and shutdown. The 25 MHz one-bit payload wire limit alone
is 611.072 ms. These are models derived from existing throughput, not new RAW
write measurements. RAW versus PNG changes card behavior and transfer boundaries.

Even if the card were already ready and output started at the first byte, only
57,931 bytes could drain during 21.861 ms at the measured rate. About 1,851,669
bytes would still be buffered at frame end. Waiting for a complete first 32 KiB
chunk raises the idealized backlog to about 1,852,663 bytes. Thus two 32 KiB
buffers cannot retain this capture burst. A full packed frame is a simple,
robust prototype allocation and already saves over 1 MB. Lower RAM requires a
much slower sensor readout, much faster output, or additional memory; the CSI
input has no downstream backpressure to stall a frame when SD pauses.

Even ideal 4-bit at 25 MHz would take 152.768 ms for this payload and leave
roughly 1.636 MB queued after the generous capture window. It helps throughput
but does not solve small-buffer capture by itself. Four-bit remains a separate
wiring/mode qualification; this audit does not enable it.

For comparison, the optimized PNG experiment's 1,026,718-byte image has a
435.078 ms CPU median and an approximately 448.927 ms two-buffer model. Thus
packed RAW eliminates pixel computation and scene-dependent compression cost,
but may be slower than a successfully overlapped optimized PNG pipeline on this
one-bit bus. Neither DMA pipeline has yet been measured end to end, and CPU-time
savings cannot be converted directly into energy savings.

## Hardware and code constraints

1. **Normal RAW10 dump expands to 16 bits.** RM0486 Rev4 pp1843-1844 and p1922
   state that 10/12/14-bit monochrome/Bayer formats are padded to 16. P0PPCR.PAD
   selects left versus right alignment; it is not a packed enable. The ongoing
   byte-oriented CSI/DCMIPP test must prove an alternative interpretation. A
   valid image plus exact byte count/test-pattern comparison is stronger than
   merely seeing a changed dump count.
2. **Pipe0 double buffering is frame-sized.** RM0486 p1844 and P0PPCR.DBM on
   p1922 switch base addresses on each frame. The line-wrapping ping-pong feature
   described on p1870 is explicitly for pixel pipes, not dump Pipe0. Do not
   assume Pipe0 can overwrite alternating 32 KiB strips in a single frame.
3. **Pipe0 has useful line events.** P0PPCR.LINEMULT can signal every 1,2,4,8,16,
   32,64,128 completed lines, plus the final partial group (pp1916,1922). Use
   these to publish an immutable completed prefix of a linear frame buffer.
   Confirm by test that event-observed prefixes are already committed to RAM
   and never change later, including under SD DMA bus contention. P0DCCNTR is
   frame-shadowed at FrameEnd (p1843); do not treat it as an assumed live DMA
   producer pointer without a separate register-behavior test.
4. **No camera backpressure.** RM0486 p1870 says camera input is continuous and
   cannot wait/hold for downstream memory. Overrun can delete pixels. Preserve
   and report all CSI/DCMIPP error flags during overlap tests.
5. **Current SD writes are synchronous CPU FIFO polling.**
   `firmware/sd-storage/sd_card.h:6` and `sd_card.c:222` expose no async operation.
   `transfer()` waits ready, issues CMD24/CMD25, fills the 256-word FIFO, waits
   DATAEND plus idle DPSM, sends CMD12 for multiblock requests, then checks CMD13
   ready/TRANSFER and DAT0 high. `SD_MAX_TRANSFER_SECTORS=64` limits each hardware
   request to 32 KiB. `sd_diskio.c` and `photo_fs_append()` retain that bound.
6. **Use SDMMC internal DMA, not a generic assumed double-buffer mode.**
   RM0486 section30.5.6 pp1401-1404 defines single-buffer or linked-list IDMA,
   16-beat bursts, and word-aligned data addresses. Linked buffers are a multiple
   of 64 bytes; IDMABNDT has 11 bits (pp1450-1452). The first buffer must already
   be ready. ABR=0 on a subsequently loaded descriptor is an IDMA transfer error,
   not an indefinite wait for the producer. An exhausted linked list before DLEN
   is also an error. Never predeclare unfinished camera bytes as ready.
7. **Card busy remains real.** RM0486 pp1392-1393: after every transmitted block
   and CRC, the DPSM waits for the card's non-busy DAT0 state before sending the
   next block. IDMA may prefetch into the host FIFO; the camera may fill RAM in
   parallel; neither allows the host to send through an asserted card busy.
   Internal card caching/program overlap is card-managed. Our driver does not
   enable optional cache or promise concurrent physical NAND programming.
8. **Cache and ownership matter.** Capture DMA writes RAM and SD IDMA reads RAM.
   Use a common suitable noncacheable frame region initially, or establish the
   required clean/invalidate/barrier sequence with no dirty CPU aliases. There
   need not be a CPU pixel copy between the two DMA engines. Descriptor metadata
   requires its own ordered publication/cache handling. Do not change cache
   ownership in a way that violates existing recovery/SAVE/shutdown guards.
9. **Current SD and file setup start after capture.** Normal v66c measured
   approximately 98-110 ms for cold SD init, 1.5-1.7 ms mount, and a separate
   60.3 ms example for free-space/name/file open. Current camera frame completion
   is around 46 ms after input-power threshold. SD init started concurrently
   at power-up would still not finish before this frame on the observed card.
   `sd_init()` also includes explicit 1+10+1 ms settling/clock delays and ACMD41
   ready polling. Keep first exposure independent of card readiness. Begin SD
   init after the critical camera-start work and advance it while DCMIPP owns
   acquisition; accept full-frame buffering when init is slower than readout.
10. **FAT is not a queued async interface.** `photo_fs.c:86` scans space/names and
    creates a temporary file. `photo_fs_append()` calls synchronous FatFs f_write.
    `FF_USE_EXPAND` is currently 0. Do not make disk_write return early while
    FatFs may reuse its buffers or advance state. First retain a blocking API
    around IDMA completion: camera still runs independently. A long contiguous
    stream needs explicit file allocation/extents and metadata finalization, or
    a separate reserved raw-block area. Neither should silently overwrite a
    mounted FAT volume. Keep the current TMP-to-final commit shape if using FAT.

## Recommended staged implementation

1. Prove actual packed RAW10 into one contiguous RAM buffer, without SD changes.
   Use a sensor test pattern where possible, expected MIPI RAW10 packing, dump
   byte count, frame geometry, canaries, and all CSI/DCMIPP errors. Decode on the
   host and compare exact samples, not just a visually plausible image. Validate
   line boundaries, packet/header exclusion and final-byte behavior.
2. Save that retained packed buffer to SD as a RAW file with the existing driver.
   This isolates storage representation from concurrent hardware changes and
   gives real raw throughput/energy. Read the complete file back and compare
   every byte against RAM. Do not hash every pixel in the normal runtime path
   merely to qualify a bench experiment.
3. Add single-buffer SDMMC IDMA for completed 32 KiB ranges. Keep the public
   synchronous API/finite timeout/abort/ready semantics initially; it can wait
   via interrupts rather than repeatedly copying words into FIFO. Verify exact
   data with unaligned-length final sectors and preserve card-idle proof.
4. Add capture line-event publication and let storage consume only complete
   ranges while camera DMA fills subsequent memory. Maintain monotonically
   increasing produced_bytes and submitted/completed_bytes, never overwrite
   consumed or in-flight regions, and finalize only after frame validation plus
   storage completion. A capture error after partial SD output must leave an
   incomplete object, never a falsely successful photo.
5. Only if command gaps matter, qualify a larger CMD25 transfer plus a static or
   safely published linked list over the completed linear buffer. With a fast
   producer and slow SD, completed data quickly gets far ahead; no ring overwrite
   is needed. With cold initialization, the whole frame may already be complete
   before the first SD request. Test long-busy and injected producer delays so
   descriptor availability failure is a controlled error, not stale-data output.

512 bytes is the device logical sector, not the best software transfer size.
One command per sector repeats setup/ready/stop costs. Keep larger multiblock
requests such as current 32 KiB. Pixel groups and rows may cross SD sector
boundaries without altering bytes. 64 image rows are 89,600 bytes = 175 sectors,
but that exceeds the current 64-sector request cap; use line events as readiness
watermarks and split into sector-aligned transfers. Tail 352 image bytes need a
512-byte staging sector/padding, or ordinary FatFs partial-sector handling.

## Measurements to log

- Power threshold/reset, sensor start/exposure, first received line, every
  producer watermark, frame complete, SD init complete, file/extents ready,
  each IDMA start/buffer release/DATAEND, final card-ready and shutdown.
- Produced/submitted/completed byte counts, minimum/maximum queue depth, largest
  card-busy interval, CPU active/wait time, no FIFO under/overrun/CRC/AXI errors.
- Exact readback and decode versus retained frame/test pattern; final tail,
  canaries, original photos preservation if using FAT, and recovery from normal
  success and each bounded failure point.
- Full cold-cycle energy on the same measured JS-fed branch, separately from
  steady already-initialized SD throughput. Do not describe that branch as
  isolated MCU or production-battery energy.
