# RAM-only packed RAW10 capture experiment

The parent bench controller executed these builds; this subtree's builder and
tests are offline only. No experiment links an SD or NOR command implementation.
The installed v66c normal capture/PNG/Standby sector and its UART recovery remain
unchanged. A fresh reset into that exact recovery, followed by the qualified
1324-byte SRAM bootstrap, is required before each RAM experiment.

The experiment explicitly pulses sensor XSHUTDOWN for at least 102 nominal
microseconds, configures the sensor using the frozen v66c register sequence, and
then starts the qualified v41 receiver sequence. These timings are deliberately
not cold-start benchmarks. The capture receives a single frame, checks byte
count, guards and errors, stops the DCMIPP pipe, disables physical data lanes only
after idle checks, stops the sensor, and parks awake with caches disabled.

| Build | Sensor payload | Packet data type | CSI format | DMA bytes |
| --- | --- | --- | --- | --- |
| `native10-diagonal-v4` | RAW10 test pattern | `0x2B` | BPP10 | 3,055,360 |
| `opaque8-diagonal-v4` | Same RAW10 test pattern | `0x30` | BPP8 | 1,909,600 |
| `opaque8-scene-v4` | RAW10 real scene | `0x30` | BPP8 | 1,909,600 expected |

The opaque mode keeps sensor FORMAT_CTRL `0x030A=10` and changes its independently
configurable OIF_IMG_CTRL `0x030F` packet type to user-defined `0x30`. CSI BPP8 and
Pipe0 DTIDA `0x30` preserve the payload's original four-high-byte/one-low-byte
groups instead of expanding each pixel to 16 bits. PAD is not a packing switch.

The current test deliberately allocates the full 3,055,360-byte frame region in
both modes. It permits that many DMA bytes and places canaries both at the
expected packed end and at full allocation end. Thus an unexpected expansion
cannot be mistaken for a successful packed frame because of a short DMA limit.
The successful packed result demonstrates reduced DMA bytes; reducing the actual
production allocation is a subsequent integration change.

## Hardware evidence available when this note was written

`../bench/native-pattern02/verified.json` and
`../bench/packed-pattern01/verified.json` report one complete frame, zero errors,
unchanged canaries, exact expected DMA counts, and two byte-identical complete
host readbacks. After independently unpacking the packed frame, all 1,527,680
samples exactly match the padded16 control. The independent scalar decoder and
the parent's NumPy decoder agree on every pixel. Decoded little-endian16 SHA-256:

`ef7a83538c1f716a686e145a1b99f3dfc0fc20168454ff1406ea77706c95880d`

The test pattern contains 960 unique values (64 through 1023) and all four
low-two-bit combinations, so the comparison exercises the extra two sensor bits.
The diagonal pattern follows ST's shipped VD6G driver: `0x0400=0x0121`, Duster
`0x0318=0`, DarkCal `0x0340=2`; all three registers were read back and checked.
This avoids silently choosing between contradictory pattern-code tables in
UM2602. Pattern success is not a real-scene or SD pipeline test; parent evidence
may subsequently add those independently.

## Memory and request contract

- Frame: `0x34000000`, capacity 3,055,360 bytes plus 32-byte canary.
- Receiver vector/code: `0x34300000`; stack `0x343AF000..0x343B0000`.
- Request: `0x343FD000`, 16 bytes `{RPQ1, nonce, mode, pattern}`.
- Proof: `0x343FD100`, 40 words. `protocol.py` defines the exact schema.
- RAW10 detail: `0x343F6000`; words 10..13 are allocation guard, pattern,
  Duster, DarkCal; words 14..18 record pre-cleanup CONTROL/FPCCR/CPACR/MSPLIM/MSP.
- The sole mutable initialized-data word is `SystemCoreClock` (64 MHz initial,
  400 MHz after clock discovery). Manifests identify its address and the immutable
  executable prefix separately; pre-execution verification covers the whole file.
- Request and proof lie beyond all linker BSS/stack/frame regions and survive
  receiver startup without a BSS clear.

## v3 completion refusal and v4 correction

The v3 control captured valid geometry/error-free data and safely stopped, but
refused final publication with `result=0x204`: HAL clock calculations had used FP
instructions, leaving CONTROL `0x0C` and CPACR `0x00F00000`. Its rejection remains
recorded in `../bench/native-pattern01/` and was not recast as a v4 success.

The v4 non-returning experiment owns the FP state it created. After safe sensor
and receiver stop, it records that state and checks privileged MSP ownership,
no active exception, interrupts masked, no FAULTMASK, no lazy FP stacking,
CONTROL containing only FPCA/SFPA, and the exact enabled CPACR. Only then does
integer assembly clear CONTROL and disable FP access. No FP instruction or
function call occurs after cleanup. Success is published with CONTROL and CPACR
both zero. This is not a helper that may normalize an arbitrary caller's state.

## Offline checks

Run `test_protocol.py`, `test_artifacts.py`, and `verify_decode.py`. They cover
request/proof rejection, exact frame counts and guards, cache/context rejection,
all three v4 binary/source hashes and memory ranges, storage-symbol exclusion,
post-cleanup instruction checks, and 4096 independent scalar RAW10 vectors.
`packed-pattern01-independent-decoder.json` records the actual-frame comparison.

`build.py --out <new-folder> --mode native10|opaque8 --pattern scene|diagonal`
recreates a fresh experiment from hash-checked frozen v66c sources. Existing
build directories are never overwritten. Initial v1/v2 build-only failures and
v3 diagnostic builds remain in this temporary workspace for provenance; v4 is
the qualified completion implementation.
