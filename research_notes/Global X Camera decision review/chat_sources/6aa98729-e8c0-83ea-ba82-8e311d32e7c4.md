USER: Is rust bare metal firmware dev well supported on st32n6?

ASSISTANT: **Yes—assuming STM32N6, bare-metal Rust is now a realistic choice.** I would describe the support as **substantial, but still worth validating peripheral-by-peripheral**, rather than uniformly turnkey. Importantly, N6 support is in **Embassy’s published 0.6.0 release**, not merely an experimental fork. :chatgpt-content-reference{index="0"}

### What is supported

| Layer | Current status |
|---|---|
| **Compiler / CPU** | Rust supports the Cortex-M55 using the standard `thumbv8m.main-none-eabi` / `thumbv8m.main-none-eabihf` bare-metal targets. This supports `no_std` firmware; an operating system is not required. :chatgpt-content-reference{index="1"} |
| **Direct register access** | The `stm32n6` peripheral-access crate provides generated register APIs for N645, N647, N655, and N657. This is useful for writing your own low-level drivers without adopting a larger framework. :chatgpt-content-reference{index="2"} |
| **Higher-level drivers** | `embassy-stm32` supports N6. Its current N657 documentation includes GPIO, UART, SPI, I²C, timers, DMA, ADC, USB, Ethernet, SDMMC, XSPI, and other peripherals. That establishes driver availability—not that every operating mode has been thoroughly validated. :chatgpt-content-reference{index="3"} |
| **Debugging / programming** | `probe-rs` has explicit N6 support. Version 0.32.0, released July 22, 2026, includes N6 reset-sequence fixes and an updated external-flash programming algorithm. :chatgpt-content-reference{index="4"} |
| **Board startup / boot examples** | Embassy has examples for both **STM32N6570-DK** and **NUCLEO-N657X0-Q**, including direct-to-RAM development and a separate external-flash boot example. :chatgpt-content-reference{index="5"} |

**Using Embassy does not force you to use its async executor.** Its HAL offers blocking as well as async APIs, so a conventional bare-metal main loop and interrupts remain an option. :chatgpt-content-reference{index="6"}

### The N6-specific peripherals are no longer entirely DIY

The **current development documentation** includes native Rust drivers for:

- **MIPI CSI-2 and DCMIPP:** The CSI driver manages the receiver and D-PHY configuration; DCMIPP handles the image-to-memory pipeline. Notably, **Pipe0 supports raw dumping without ISP or color conversion**, which is relevant to a capture-and-store camera. :chatgpt-content-reference{index="7"}
- **Neural-ART NPU:** There is an async driver for executing epoch-controller command streams produced by ST’s Edge AI tooling. However, it explicitly does **not** support networks compiled into the alternative streaming-engine epoch mode, and memory permissions/cache setup remain application responsibilities. :chatgpt-content-reference{index="8"}

Those are references to the **git documentation**; do not assume every API there is present in a particular released crate.

### Where I would budget integration work

**Boot and memory setup deserve attention.** Embassy’s external-flash example uses a first-stage bootloader running in SRAM, initializes NOR flash into memory-mapped mode, and then starts the application. Its tooling also handles the boot-ROM image headers/signing step. You have a reference implementation, but this is more involved than simply placing an application in internal flash. :chatgpt-content-reference{index="9"}

**Driver availability is not equivalent to maturity.** For example, an open N6-specific report describes intermittent hangs during blocking SPI reads on the Discovery board. That does not establish that all SPI configurations or current revisions are affected, but it is a reason to stress-test your exact configuration. :chatgpt-content-reference{index="10"}

### My recommendation

For a new project, I would start with Embassy’s **`examples/stm32n6` RAM-loaded examples**, prove the required peripherals, then move to **`examples/stm32n6-flashboot`** and test real power-on operation. Pin the dependency version or commit that you validate. Both starting points already exist upstream. :chatgpt-content-reference{index="11"}

**Bottom line: Rust support is good enough that I would not reject the STM32N6 over language support. For minimal register-level firmware, it is a credible choice; for a complete camera/NPU application, I would first validate that exact data path before committing the hardware.** This assessment is based on the current source and documentation, not a hardware test.
